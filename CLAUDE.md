# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Widgets for the **Cefalot** no-code widget platform (a strict built-in HTML/CSS parser + JS click handlers — see `.claude/agents/cefalot-widget-developer-v4.md` for the full platform rules). Each subdirectory under the project root (currently `changan/`, `haval/`, `jaecoo/`, `jeland/`, `omoda/`, `tenet/`, `tenet-2/` — one per dealership brand) holds one project's set of widget-state bundles plus a `concept/` folder. `_kit-forms/` and `_kit-catalog/` in the repo root are the shared, cross-project reference kit — see below.

## Primary workflow: "создай виджет для <сайт>, список форм: <формы>"

When the user opens a new session and gives a prompt shaped like *"создай виджет для \<сайт\>, список форм: \<форма1\>, \<форма2\>, ..."*, do this directly — no need to go through Claude Design/`concept/` first (that path is opt-in, only when the user explicitly hands you a concept):

1. **Read `.claude/agents/cefalot-widget-developer-v4.md` in full first** — it's the authoritative, evolving spec (file/folder structure, wrapper rules per bundle type, checkbox pattern, allowed/forbidden tags, `data-widget-*` attributes with their value requirements, the canonical class/variable-name dictionary). Don't rely on memory of past sessions — it gets amended over time.
2. **Ask the user one block of questions before any research or generation** — for a genuinely new project (new dealer/brand), always ask, together, in one message: (a) the list of forms/catalogs if not already given in full, (b) the brand font name, (c) the exact consent-checkbox wording for each form. These three are **never** derived by scraping the reference site or invented — see agent file section 0b for why and for the narrower rule when adding one new form to an already-started project (font already fixed, only that form's checkbox text needs asking).
3. **Research the reference site's remaining style AND real content** with WebFetch/browser — colors, real computed border-radius/`clip-path` (reproduce literally, don't smooth into a generic rounded scale), spacing scale, general visual language, plus concrete facts a form needs: dealer/brand name, phone/address if there's a specific dealer, model lineup with real names, actual promo copy. If a fact isn't published anywhere on the real site (e.g. working hours, a specific discount deadline), don't invent a specific-sounding value — use neutral, non-committal copy instead. No Claude Design step for this trigger phrase.
4. **Write `<project_dir>/DESIGN-TOKENS.md` before any HTML/CSS** — using the canonical variable names from agent file section 8, values from steps 2–3's answers/research. This is a hard gate: the platform gives every bundle's CSS an independent, non-shared file, so this document is the only thing standing between the project and per-form visual drift. Every bundle generated afterward copies its `:root, :host {...}` block from this document verbatim.
5. **Check the target project folder** for existing numbered bundles before creating new ones — don't silently overwrite an existing `N - name` folder; if a requested form looks like it might collide with or duplicate an existing bundle, ask the user rather than guessing.
6. **Use the repo-root `_kit-forms/`/`_kit-catalog/` as the structural source for every form** — copy their HTML structure and exact class/variable names, substituting only this project's token values and content. Do not re-derive markup per project. If the kit is missing a pattern this project genuinely needs, add it to the root kit (not just the project) and say so. See agent file section 0.
7. **Generate each requested form** as its own `N - name` folder per the agent's file/folder-structure rules — one shared `0 - меню` if there's more than one form, one shared `00 - <название спасибо>` success screen, and `1, 2, 3, …` for the individual forms/catalogs in the order given.
8. **If generating multiple sibling forms via parallel subagents, pin every project-wide decision explicitly in each agent's prompt** — don't leave it to "use the recommended pattern." Independent agents resolve the same ambiguity differently even when each one's reasoning is individually sound. Pin, per project, in every parallel prompt: the mobile hero text-placement pattern, whether both consent checkboxes are `required`, the exact close-button positioning mechanism, and that structure/class/variable names come from the root kit — see agent file section 9.
9. **After parallel generation, do one reconciliation pass across all sibling bundles before calling the project done** — diff the shared-decision points from step 8 (mobile hero pattern, checkbox `required`-ness, close-button inset, token values) across every bundle and fix whichever ones drifted. This has caught real inconsistencies every time it's been done (e.g. `jeland`: two forms used a different mobile hero pattern than the other two, and the second consent checkbox was `required` in some forms but not others).
10. **When told to mirror another project's current structure "exactly," verify that project's actual current files (Read/Glob) rather than trusting its own `DESIGN-TOKENS.md` or prior chat summaries** — a reference project's documentation can lag behind real edits made outside your session. The actual files in the reference project are always the source of truth over what any doc claims about them.
11. **Do not build or send the visual preview (`_tools/build_widget_preview.py`) unless the user explicitly asks for it in that session** — this used to be a standard closing step; the user removed it from the default workflow. Just report what was generated in text.
12. Report back per-bundle what was generated and flag anything you're unsure about (e.g. a form whose "no live JS calculation" constraint changes its content, per the checklist in the agent file).

## Folder structure convention (per project, e.g. `tenet/`)

- `0 - меню` — main routing/menu screen (only needed if the project has more than one form). Unlike every other bundle type, this is NOT 4 files — it's 4 files **per enabled state** (`compact.desktop.html/css`, `compact.mobile.html/css`, and optionally `expanded.*`/`closed.*`) — see agent file section 2a.
- `00 - <название>` — shared "thank you" screen, one per project, reused across all forms.
- `1 - …`, `2 - …`, … — individual forms/catalogs, numbered in the order they were added (number is not tied to form type).
- `concept/` — raw Claude Design output, dropped in by the user or produced via `/design` when explicitly asked for a visual concept first. **Never edit files in `concept/` in place** — it's reference input, not something to fix; generate a separate `N - name` folder instead. `concept/INSTRUCTIONS-FOR-CLAUDE-DESIGN.md` is the brief template for that opt-in path.
- `DESIGN-TOKENS.md` — this project's token values, in the canonical variable names from the root kit.

Repo root also has `_kit-forms/`, `_kit-catalog/` — the **shared, cross-project** structural reference (HTML markup + class/variable names), not project-local and not upload-ready bundles. Every project's real forms copy structure from here; only token values and content differ per project. The 7 existing projects predate this shared kit and are not retrofitted to it — the rule applies going forward. See agent file section 0.

Full rules (structure, CSS scoping, checkbox pattern, allowed/forbidden tags, `data-widget-*` attributes, catalog attributes, canonical naming) live in `.claude/agents/cefalot-widget-developer-v4.md` — that file is the source of truth, not this one; don't duplicate its content here as it will drift out of date.

## Visual preview tooling

`_tools/build_widget_preview.py` — generic, works on any project folder. For each `N - name` bundle it reads `desktop.html`/`desktop.css`/`mobile.html`/`mobile.css` (or, for a menu bundle, `<state>.desktop.{html,css}`/`<state>.mobile.{html,css}` per enabled state), wraps each in the correct platform wrapper classes for its bundle type, and mounts them all as isolated `<iframe sandbox="allow-scripts" srcdoc>` panes in two live device simulators (desktop 16:9 site mockup + mobile phone mockup). A small runtime script is injected into each iframe that emulates the platform's own click handling (`data-widget-form`/`-submit`/`-close`/`-state-action`/catalog substep nav) and `postMessage`s intents up to the parent, which actually switches which iframe is showing — so the whole thing is genuinely clickable end-to-end (menu compact↔expanded, → form, → submit → success, catalog substeps with real "not visited yet" gating). Cross-bundle `data-widget-form="FORM_ID"` routing reads `<project_dir>/_preview-form-map.json` (create/update by hand — this ID↔folder link only exists in the real Cefalot admin, not in any file).

Usage: `python3 _tools/build_widget_preview.py <project_dir> <out_html_path> [project_title]`. **Only run this when the user explicitly asks for a preview in that session** (see primary-workflow step 11). When run, deliver the output via `SendUserFile`, never `Artifact` — the Artifacts platform's CSP does not render nested `<iframe sandbox="allow-scripts">` content at all. This script itself is not a Cefalot upload artifact — it's purely a local dev tool.
