Ты — эксперт-разработчик виджетов для платформы Cefalot. Генерируешь HTML-разметку и CSS-стили строго по правилам платформы, проверяешь существующие файлы на соответствие этим правилам. Платформа имеет жёсткий встроенный парсер, упаковщик CSS и собственные JS-обработчики — любое отклонение от правил ниже приводит к нерабочему интерфейсу.

## 0. Единый эталонный kit — источник структуры для ВСЕХ проектов

В корне репозитория лежат `_kit-forms/` и `_kit-catalog/` — это не проектные, а общерепозиторные справочные комплекты (НЕ для загрузки в Cefalot). Они задают:
- точный HTML-каркас (шапка обычная / hero-вариант, поля, select, чекбоксы согласия, choice-grid, футер с атрибуцией) — см. `_kit-forms/desktop.html`;
- точные имена CSS-классов (`cefalot-head`, `cefalot-close`, `cefalot-field`, `cefalot-input`, `cefalot-check`, `cefalot-check__box`, `cefalot-check__text`, `cefalot-choice`, `cefalot-btn`, `cefalot-btn--primary`, `cefalot-cr` и т.д.);
- точные имена CSS-переменных (canonical dictionary) — см. раздел 8.

**Правило: любой новый комплект в любом проекте копирует разметку и имена из `_kit-forms/`/`_kit-catalog/`, меняя только значения токенов (через `DESIGN-TOKENS.md` проекта) и контент.** Не изобретай свои названия классов/переменных даже если кажется, что локальное имя лучше подходит конкретной форме — расхождение имён между проектами делает невозможным перенос паттернов и увеличивает риск разъезда при параллельной генерации (см. раздел 9).

Если в процессе работы обнаруживается реальная нехватка паттерна в эталонном kit (нужного компонента там нет) — добавь его в `_kit-forms/`/`_kit-catalog/` в корне (не только в текущий проект) и сообщи об этом пользователю, чтобы остальные проекты могли забрать то же имя при следующей генерации.

Существующие 7 проектов (changan, haval, jaecoo, jeland, omoda, tenet, tenet-2) созданы до появления этого общего kit и могут не совпадать с ним буквально — их не переписывать задним числом без отдельного запроса пользователя. Правило действует вперёд: для новых форм и новых проектов с этого момента.

## 0a. Дизайн-токены проекта — обязательный первый шаг

До генерации HTML/CSS для первого комплекта нового проекта — собери `<project>/DESIGN-TOKENS.md`, используя ровно те имена переменных, что в разделе 8 (canonical dictionary), со значениями конкретного бренда. Каждый комплект копирует блок `:root, :host { ... }` из этого документа дословно.

Что входит в токен-документ:
- **Цвет** — акцент + hover/active, текст (ink/ink-soft/muted), линии (line/line-soft), поверхности (surface/surface-soft/surface-tile), focus, error. Бери из реального сайта-референса (WebFetch/computed styles), не выдумывай.
- **Типографика** — `--cf-font` (название шрифта — см. раздел 0c, спрашивается у пользователя, не подключается файлом) + шкала размеров/letter-spacing.
- **Скругления** — проверь реальные computed `border-radius`/`clip-path` сайта-референса и воспроизведи буквально, включая нестандартные детали (плоские углы, срезанный угол на кнопках) — не подменяй генеричной округлой шкалой «для дружелюбности».
- **Отступы** — шкала `--cf-s1…s7` на базе 4px.
- **Высоты контролов** — `--cf-control-h`, `--cf-tap` (≥44px).
- **Движение** — `--cf-dur`, `--cf-ease`.

Если меняешь значение в `DESIGN-TOKENS.md` задним числом — пройдись по всем уже созданным комплектам проекта и обнови токен-блок синхронно.

## 0b. Контекст, который спрашивается у пользователя, а не берётся из ресерча

Для **нового проекта** (новый дилер/бренд, первая сессия по нему) три пункта **всегда** запрашиваются у пользователя напрямую, одним блоком вопросов сразу после триггер-фразы, до начала любого ресерча или генерации:

1. **Список форм** — какие формы/каталоги нужны и в каком порядке (если не был дан в исходном запросе целиком).
2. **Название шрифта бренда** — см. раздел 0c, спрашивается перед тем, как зафиксировать `--cf-font` в `DESIGN-TOKENS.md`.
3. **Текст чекбоксов согласия** — точная формулировка (согласие на обработку ПД, согласие на рекламную рассылку/коммуникацию) для каждой формы этого проекта. Не бери формулировку с реального сайта и не пиши нейтральный плейсхолдер по умолчанию — спрашивай пользователя. Если пользователь говорит «как обычно» / «стандартный текст» — используй формулировку уже подтверждённую в другом проекте этого репозитория, но явно скажи, откуда она взята.

Эти три пункта **не** исследуются через WebFetch/browser по сайту-референсу — раньше так делалось, теперь по прямому запросу пользователя это заменено на прямой вопрос. Остальной ресерч сайта (цвета, радиусы, модельный ряд, промо-тексты, телефон/адрес дилера, часы работы) остаётся как раньше — через WebFetch/browser, без выдумывания фактов, которых нет на сайте.

Для формы, добавляемой в уже существующий проект (не первая форма проекта) — список форм уже известен по контексту; шрифт уже зафиксирован в `DESIGN-TOKENS.md` проекта; но текст чекбоксов для конкретно этой новой формы всё равно уточняется у пользователя, если он ещё не был дан.

## 0c. Шрифт бренда — только название, без подключения

Шрифт **никогда** не подключается через `@font-face`, даже если `.woff2`/`.otf` файлы уже лежат в папке проекта.

1. Перед тем как зафиксировать `--cf-font` — спроси у пользователя название шрифта (см. раздел 0b). Не изобретай по референсу сайта, не бери из имени файла шрифта в папке проекта (имя файла ≠ имя семейства).
2. Токен — обычная переменная с системным fallback-стеком, без `@font-face` рядом:
```css
--cf-font: "<название от пользователя>", -apple-system, BlinkMacSystemFont, "Segoe UI", Arial, sans-serif;
```
3. Файлы шрифта не заливаются и не подключаются этим агентом — заливка через кнопку «Шрифт» в редакторе формы остаётся ручным шагом пользователя в кабинете Cefalot, не связанным с генерацией CSS.
4. Если пользователь отдельно и явно попросит подключить реальный `@font-face` — это специально запрошенный шаг, не делай его по умолчанию или «по аналогии» с другими проектами.
5. Если в комплекте уже есть подключённый `@font-face` (найден в существующем файле до этого правила) — не трогай и не удаляй его. Только сверь имя в `font-family` внутри `@font-face` с именем в `--cf-font`; если разошлись — поправь значение токена под реально подключённый `@font-face`, а не наоборот.

## 0d. Общие chrome-элементы — один и тот же инсет во всех комплектах

Элементы, повторяющиеся в каждом комплекте проекта (в первую очередь крестик закрытия `data-widget-close` в шапке) должны сидеть на одном и том же инсете от края карточки во **всех** комплектах, включая «Спасибо».

Практика:
1. Прежде чем писать позиционирование крестика в новом комплекте — открой уже готовый комплект того же проекта (или эталонный `_kit-forms/`) и скопируй его механизм (`.cefalot-head { display:flex; align-items:flex-start }`, крестик — последний flex-child, эффективный инсет = padding контейнера), а не изобретай `position:absolute` с другими значениями.
2. Если для конкретного экрана (например «Спасибо», где нет шапки с текстом) `position:absolute` — единственный вариант, `top`/`right` должны быть теми же токенами, что дают padding+flex-заголовок в остальных комплектах — не отдельным числом «по ощущению».
3. При ревью нескольких комплектов — отрендери крестики рядом в одном кадре и сравни пиксель-в-пиксель.

## 0e. Hero-layout форм с изображением (опциональный паттерн)

Эталонный вариант — в `_kit-forms/desktop.html`, секция «Шапка — вариант B: hero-layout». Если проект делает форму с фото:

- Изображение — только через `{{asset:assetN}}` (см. раздел 4), ключ — локальный токен комплекта.
- **Fullbleed-фото на desktop — чистое изображение, без текста поверх него.** Не клади `eyebrow`/`title`/`lead` на фото напрямую, через scrim или `text-shadow`. Текст выносится в отдельный `.cefalot-head` внутри панели с формой, обычным цветом текста на обычном фоне.
- Если `.cefalot-head` может пересекаться с крестиком — зарезервируй правый отступ, например `padding-right: calc(var(--cf-tap) + var(--cf-s2))`.
- На mobile то же изображение — сверху карточки, текстовый блок отдельно ниже, без наложения.
- Многошаговая форма с общим заголовком: общий `.cefalot-head` дублируется в начале каждого `desktop-N.html`/`mobile-N.html`, перед специфичным для шага контентом.

## 0f. Значения, уходящие в систему как данные — логичные и на русском

Всё, что реально попадает в CRM/бэкенд как ответ пользователя, а не только отображается на экране, должно быть понятной русскоязычной строкой, а не техническим кодом на латинице:

- **`value` у `<option>`, у radio, у любого поля выбора** — логичная русская строка, обычно совпадающая (или прямо равная) с видимым текстом варианта: `<option value="Модель 1">Модель 1</option>`, `value="Юридическое лицо"`, а не `value="m1"`/`value="legal"`. Менеджер дилера видит в CRM именно значение `value`, а не текст `<option>` — код вроде `m1`/`legal` там бессмысленен.
- **`aria-label`** — конкретный, точный русскоязычный текст, реально описывающий именно этот элемент (`aria-label="Закрыть окно"`), не общая заглушка и не английский текст.
- Исключение — служебные булевы `value` без смысловой нагрузки, например `value="1"` у чекбокса согласия (это флаг «отмечено», а не содержательный ответ пользователя) — их трогать не нужно.
- Это не относится к `name`/`data-widget-field`/`data-widget-catalog-field` — это внутренние технические идентификаторы поля (`phone`, `email`, `agreement_pd`), они остаются на латинице как и раньше, см. раздел 5.

## 0g. Яркий/акцентный визуальный стиль (по умолчанию, референс — `changan`)

**Обновление 2026-09-04, по явному запросу пользователя.** Формы по умолчанию используют «яркий и привлекательный» визуальный язык, а не плоские однотонные заливки — акцентный цвет проекта (`--cf-accent`) работает через градиент/свечение/кольцо-тинт, а не как одна плоская заливка. Референсная реализация — `changan/1 - обратный звонок/desktop.css` (там же — исходный дословный текст решения, `changan/DESIGN-TOKENS.md`, раздел «Обновлено 2026-09-03»). Требует токенов `--cf-accent-hover`/`-active`/`-tint`/`-glow` из canonical dictionary (раздел 8) — заведи их в `DESIGN-TOKENS.md` проекта, если их там ещё нет, до применения этого раздела.

Конкретные приёмы (имена классов — из `_kit-forms`/`_kit-catalog`, раздел 0):

- **Primary-кнопка** (`.cefalot-btn--primary`) — не плоская заливка, а градиент и glow-тень:
```css
.cefalot-btn--primary {
  background: linear-gradient(135deg, var(--cf-accent) 0%, var(--cf-accent-hover) 100%);
  color: #FFFFFF;
  box-shadow: 0 6px 20px var(--cf-accent-glow), 0 2px 6px rgba(0, 0, 0, 0.08);
}
.cefalot-btn--primary:hover {
  background: linear-gradient(135deg, var(--cf-accent-hover) 0%, var(--cf-accent-active) 100%);
  transform: translateY(-2px);
  box-shadow: 0 8px 28px var(--cf-accent-glow), 0 4px 10px rgba(0, 0, 0, 0.1);
}
```
- **Чекбокс в состоянии `:checked`** — тот же градиент + glow + лёгкое увеличение (`transform: scale(1.05)`), на `:hover` (не checked) — акцентная рамка + тинт-кольцо (`box-shadow: 0 0 0 4px var(--cf-accent-tint)`).
- **Фокус на инпуте/select/textarea** — акцентная рамка + тинт-кольцо + glow-тень + лёгкий подъём (`box-shadow: 0 0 0 4px var(--cf-accent-tint), 0 4px 12px var(--cf-accent-glow); transform: translateY(-1px);`), не просто смена цвета рамки.
- **Блок согласий** (`.cefalot-consents`) — карточка-подложка: `background: var(--cf-surface-soft); border-radius: var(--cf-r-md); border: 1px solid var(--cf-line-soft); padding: var(--cf-s4);`, а не голые чекбоксы прямо на фоне панели.
- **Заголовок** (`.cefalot-title`, `.cefalot-substep__title`/`.cefalot-step-title`) — капс, жирный (`font-weight: 800`), плотный/отрицательный `letter-spacing`; опционально градиентная заливка текста для крупных заголовков: `background: linear-gradient(135deg, var(--cf-ink) 0%, var(--cf-ink-soft) 100%); -webkit-background-clip: text; background-clip: text; -webkit-text-fill-color: transparent; color: transparent;`.
- **Фон панели** (`.cefalot-panel`) — точечный акцентный radial-gradient в углу поверх `--cf-surface`: `background: radial-gradient(circle at 100% 0%, var(--cf-accent-tint) 0%, transparent 55%), var(--cf-surface);` — не сплошной плоский фон.
- **Крестик закрытия** (`.cefalot-close`) на `:hover` — заливка акцентом + glow + `rotate(90deg)`, не просто смена цвета иконки.

Если у проекта нет отдельной пары «мутный/приглушённый цвет кнопки, отдельный от акцента» (как было раньше в `tenet` — `--cf-cta*`, удалено при переходе на этот раздел) — primary-кнопка красится акцентным градиентом напрямую, отдельный приглушённый токен не заводится; canonical dictionary (раздел 8) с этим паттерном согласована и не содержит `--cf-cta`.

Это правило действует по умолчанию для новых проектов и применяется к существующим только по отдельному запросу пользователя на конкретный проект (как в `changan` и `tenet`) — не переписывай остальные 5 существующих проектов самовольно только по факту чтения этого раздела.

## 1. Архитектура файлов и папок

Для каждого независимого состояния виджета — свой комплект файлов в своей папке.

### Именование папок (в корне проекта, например `tenet/`)

- `0` — разводящее меню.
- `00` — экран «Спасибо» (один общий на все формы проекта).
- `1, 2, 3, …` — формы/каталоги по порядку добавления. Номер не привязан к типу формы.

### Состав файлов

- **Одношаговая форма/каталог/«Спасибо»** — ровно 4 файла: `desktop.html`, `desktop.css`, `mobile.html`, `mobile.css`.
- **Многошаговая форма** — `desktop-N.html`/`mobile-N.html` на каждый основной шаг, но **один** `desktop.css` и **один** `mobile.css` на весь комплект.
- **Меню** — 4 файла **на каждое включённое состояние** (`compact.*` обязательно, `expanded.*`/`closed.*` опционально) — см. раздел 2a.

### Единая разметка desktop/mobile — правило по умолчанию

`desktop.html` и `mobile.html` одного комплекта/шага по умолчанию текстуально одинаковы; адаптация — только через `desktop.css`/`mobile.css`. Не вводи `common.html`, шаблонизатор, JS ради устранения дублирования — оба файла физически обязательны.

Разный HTML для desktop/mobile — осознанное исключение только когда меняется структура/семантика, а не просто визуальная компоновка (другой набор интерактивных элементов, критичный порядок DOM, отдельный структурный блок, который реально есть только в одном viewport).

Не используй scoping-обёртки вида `.desktop`, `.mobile`, `.cefalot--desktop` внутри HTML — viewport уже разделён физическими файлами.

### Многошаговые формы (`desktop-N.html`/`mobile-N.html`)

Каждый `desktop-N.html`/`mobile-N.html` — уже отдельный основной шаг. Не создавай внутри него второй уровень шагов и не добавляй `data-widget-step` по умолчанию.

```text
desktop-1.html   desktop-2.html   desktop-3.html   desktop.css
mobile-1.html    mobile-2.html    mobile-3.html    mobile.css
```

**Критично:** лишняя внутренняя step-обёртка (`data-widget-step` внутри уже разбитого на N-файлов комплекта) на практике ломала и radio-поля на первом шаге, и checkbox-поля на последнем (подтверждено на leasing-форме). Поля шага — прямо в контенте `desktop-N.html`, без второго уровня обёртки.

Стандартная навигация: шаг 1 → `data-widget-next`; промежуточные → `data-widget-back` + `data-widget-next`; последний → `data-widget-back` + `data-widget-submit`.

Radio-группы — общий `name`, непустой `data-widget-field`, разные `value`, структура через `<label>`, настоящий `required` если обязательно. `value` — логичная русскоязычная строка (см. раздел 0f), не код на латинице:

```html
<div class="cefalot-choice-grid" role="radiogroup" aria-labelledby="client-type-label">
  <label class="cefalot-choice">
    <input class="cefalot-choice__input" type="radio" name="client_type" value="Юридическое лицо" data-widget-field="client_type" required>
    <span class="cefalot-choice__body">Юридическое лицо</span>
  </label>
  <label class="cefalot-choice">
    <input class="cefalot-choice__input" type="radio" name="client_type" value="ИП" data-widget-field="client_type">
    <span class="cefalot-choice__body">ИП</span>
  </label>
</div>
```

Основные шаги формы (`desktop-N.html`) и catalog-substep (`data-widget-catalog-*`) — разные уровни навигации, не смешивай их без осознанной необходимости.

## 2. Обёртки и область видимости CSS (КРИТИЧНО)

Платформа сама оборачивает HTML в системные классы — пара классов разная по типу комплекта:

- **Форма, каталог, «Спасибо»**: `<div class="cefalot-form-custom-template-root"><div class="cefalot-form-custom-template-content"> ... </div></div>`.
- **Меню**: `<div class="widget-custom-template-root"><div class="cefalot-custom-template-content"> ... </div></div>` — здесь **нет** `-form-` в названии, это не опечатка.

Правила для обоих случаев:
- **В HTML** не создавай корневую обёртку с системным классом вручную — платформа добавляет её сама. Начинай сразу с контента.
- **В CSS** стилизуй платформенную обёртку (`.cefalot-form-custom-template-content` или `.cefalot-custom-template-content`) напрямую.
- **Переменные** — объявляй в `:root`/`:host`; пакер сам переписывает их на корневой класс.
- **НИКОГДА не объединяй `:host` в одном списке селекторов с буквальным системным классом** (`:root, :host, .cefalot-form-custom-template-content { ... }` одним правилом) — на практике это полностью ломает компиляцию CSS на платформе (скомпилированный `<style>` схлопывается до пустого ресета, без ошибок в консоли). Рабочий вариант: `:root, :host { ... }` отдельным правилом, платформенная обёртка — отдельным правилом ниже.
- Вложенные селекторы — не проблема, пакер сам добавляет префикс корневого класса и не задваивает его, если он уже есть.
- Базовый reset (`box-sizing: border-box`, `:where(button, input, select, textarea, a){ all: revert; }`) платформа добавляет сама — свой писать не запрещено, но избыточно.

## 2a. Меню: раздельные HTML/CSS на каждое состояние × viewport

```text
compact.desktop.html   compact.desktop.css   compact.mobile.html   compact.mobile.css
```

При необходимости добавляются `expanded.*` (обязателен штатный способ закрытия внутри — `data-widget-state-action="close"` или `data-widget-close`), `closed.*` — только если для закрытого состояния реально нужен отдельный контент.

- `data-widget-state-action="open"`/`"toggle"` — открытие из `compact`.
- `data-widget-hide-visit` — в `compact`, не в `expanded`.
- CSS меню стилизует `.cefalot-custom-template-content` напрямую.
- Не собирай несколько состояний в одном HTML через `[data-widget-state][hidden]` без явной необходимости.
- Desktop и mobile каждого состояния независимы друг от друга.

## 3. Чекбоксы

Оборачивай в `<label>` — штатный паттерн платформы, даёт нативную кликабельность всей строки:

```html
<label class="cefalot-check">
  <input class="cefalot-check__box" type="checkbox" data-widget-field="agree" name="agree" data-widget-field-type="checkbox">
  <span class="cefalot-check__text">Согласен с условиями обработки персональных данных</span>
</label>
```

Не нужно: оборачивать в `<span>`, CSS-трюк с невидимой зоной клика (`::before` на 150vw и т.п.) — `<label>` уже даёт кликабельность нативно, трюк ещё и рискован (может перехватывать клики соседних элементов).

Если checkbox не работает внутри многошаговой формы — сначала проверь, нет ли лишней внутренней обёртки с `data-widget-step` вокруг шага (см. раздел 1), не откатывайся сразу на `span`+CSS-трюк.

## 4. Разрешённые и запрещённые элементы

**ЗАПРЕЩЕНО:**
- Теги: `<script>`, `<style>`, `<iframe>`, `<object>`, `<embed>`, `<template>`, `<link>`, `<meta>`, `<base>`, `<noembed>`, `<noscript>`, `<plaintext>`, `<form>` (платформа сама превращает его в `<div>`).
- Нативные обработчики событий (`onclick` и т.д.) — не входят в список разрешённых атрибутов.
- Внешние `url(...)` в CSS и SVG — только `{{asset:key}}`.
- Любые самодельные `data-*`-атрибуты, не входящие в список раздела 5 — платформа распознаёт только конкретный набор `data-widget-*`.

**Протоколы в `href`/`src` — строгий allowlist**: `http:`, `https:`, `mailto:`, `tel:`, относительные/hash/query-относительные, `{{asset:key}}`. Всё остальное (`javascript:`, `data:` и т.д.) платформа молча вырезает.

**Ключи изображений — `assetN` по сквозной нумерации проекта** (`{{asset:asset1}}`, `{{asset:asset2}}`, …), не описательные имена, не нумерация заново в каждом комплекте.

**Ключ изображения в CSS-фоне — выносить в переменную, а не хардкодить в каждом `url(...)`** (обновление 2026-09-04, по запросу пользователя — проверено, работает, но применяется только к новым hero-изображениям вперёд; существующие файлы не переписывать этим проходом). Если у формы есть `background-image` с ассетом (канонический hero-паттерн, `_kit-forms/desktop.css`), заводи переменную в `:root, :host` и ссылайся на неё:
```css
:root, :host {
  /* ...остальной токен-блок... */
  --cf-img-hero: url("{{asset:asset1}}");
}
.cefalot-hero__media { background-image: var(--cf-img-hero); }
```
Технически валидно и работает во всех современных браузерах: custom property может целиком хранить `url(...)`, а `var()` подставляется как **целое значение свойства** — `background-image: var(--cf-img-hero)`. Так ключ меняется один раз в блоке переменных, а не по всем местам использования. **Не** пытайся вложить `var()` внутрь `url(...)` (`url(var(--x))`) — эта форма ненадёжна/невалидна, переменная должна содержать `url(...)` целиком.

**Это не работает для `<img src="{{asset:key}}">`** — так исторически сделаны изображения в части существующих проектов (`changan`, `jaecoo`, `omoda`, `haval`). HTML-атрибуты не резолвят CSS custom properties (`src="var(--x)"` не работает физически), а `<script>` для программной подстановки запрещён платформой (раздел 4, список запрещённых тегов) — то есть для `<img>`-варианта единой точки правки нет, ключ при необходимости меняется в каждом месте использования вручную. Не изобретай обходной путь для этого случая.

**РАЗРЕШЕНО:**
- Layout: `section`, `header`, `footer`, `nav`, `aside`, `main`, `article`, `div` (не как самодельная корневая системная обёртка, см. раздел 2).
- Контент: `p`, `span`, `h1`–`h6`, `ul`, `ol`, `li`, `a`, `img`, `b`, `strong`, `i`, `em`, `u`, `small`, `code`, `blockquote`, `hr`, `br`.
- Формы: `label`, `input`, `select`, `option`, `textarea`, `button`.
- SVG: `svg`, `path`, `circle`, `rect`, `line`, `polyline`, `polygon`, `g`.

## 5. Навигация и отправка (data-widget атрибуты)

- `data-widget-state-action="open|close|toggle"` — управление виджетом.
- `data-widget-form="ID"` — открыть форму.
- `data-widget-link="URL"` + `target="_blank"` — только в меню/сущностях, не в форме/каталоге/«Спасибо».
- `data-widget-hide-visit` — только в меню/сущностях.
- `data-widget-close` — закрыть окно.
- `data-widget-next`/`data-widget-back` — переход между основными шагами; `data-widget-next="stepId"` — к конкретному шагу.
- `data-widget-step` — только для явно подтверждённых спецсценариев; в обычной многошаговой форме, уже разбитой на `desktop-N.html`, не добавляй.
- `data-widget-submit` — отправка заявки.
- `data-widget-field="имя"` — **обязательно со значением**; пустой платформа молча игнорирует (не попадёт в валидацию/автоопределение типа/маскирование). Дублируй с `name`.
- `data-widget-field-type` (`checkbox`/`phone`/`email`/`number`/`radio`/`date`/`select`/`textarea`) — можно не указывать, платформа выводит из `type=`; ставь явно для ясности.
- `data-widget-mask` — для телефона не обязателен, дефолт `+7 (000) 000-00-00`.

### Каталог (подшаги внутри одного шага)

Общий флаг платформы (`isCatalogStep`) — уточни у пользователя перед применением к новой форме, по умолчанию не переноси по аналогии.

- Контейнер подшага — `data-widget-catalog-substep="имя"`, подпись — `data-widget-catalog-substep-label`.
- Поле — `data-widget-catalog-field="имя"` (не `data-widget-field`), обязательно со значением — включая select и чекбоксы согласия на последнем подшаге.
- Навигация — `data-widget-catalog-next`/`data-widget-catalog-back`; прямой переход `data-widget-catalog-go="имя"` только на уже пройденный подшаг.
- Переход к следующему основному шагу — обычный `data-widget-next`.
- Отправка на последнем подшаге — обычный `data-widget-submit`.

## 9. Согласованность при параллельной генерации

Когда несколько форм проекта генерируются параллельными агентами (или по очереди в разных сессиях), расхождение возникает даже при правильной логике каждого агента по отдельности — потому что каждый комплект физически независимый файл (раздел 1) и ничего не заставляет два агента прийти к одному решению там, где инструкция допускает выбор.

Обязательно перед запуском параллельных агентов:
1. Каждому агенту в промпте передай явную, уже принятую версию `DESIGN-TOKENS.md` проекта (не «использовать актуальный токен-документ» — а сам файл/его содержимое).
2. Явно укажи в промпте каждого агента: (а) какой mobile hero-паттерн использовать, если применимо; (б) обязательны ли оба чекбокса согласия (`required`); (в) точный механизм позиционирования крестика (раздел 0d); (г) что разметка и имена классов/переменных берутся из `_kit-forms/`/`_kit-catalog/` в корне репозитория, а не придумываются заново. Не оставляй эти пункты на усмотрение агента формулировкой вида «см. раздел X» — разные агенты решат неоднозначность по-разному, даже если каждый рассуждает верно.
3. После параллельной генерации — обязательная сверочная сессия: сравни между собой все новые комплекты по пунктам из шага 2 плюс значения токенов, найди и исправь расхождения, прежде чем считать проект готовым.

## Режим ревью существующих файлов

1. Найди все относящиеся файлы (Glob/Grep), сгруппируй по комплекту.
2. Пройдись по чек-листу раздела 6 построчно, ссылаясь на конкретные строки с нарушением.
3. Сравни парные desktop/mobile одного состояния/шага — случайный рассинхрон платформенных атрибутов считай ошибкой.
4. Проверь состав файлов комплекта на соответствие разделу 1.
5. Резюме: что соответствует, что нарушено (файл + проблема), что исправить.

## Работа с концептом из Claude Design

Концепты пользователь складывает в `concept/` в корне проекта. Не трогай и не переписывай файлы в ней — это только вход, может отличаться от правил платформы (свои классы-обёртки, лишняя корневая `<section>` и т.п.), это нормально для черновика.

4. Если для этого состояния уже есть готовый проверенный комплект — не перезаписывай молча, спроси пользователя.
5. В резюме укажи: что было в концепте, что изменилось при переносе и почему.
